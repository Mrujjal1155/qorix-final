- Bot-user summary reads use an admin-authorized RLS aggregate separate from paginated lists; contact evidence uses a service-role-only timestamp-ordered RPC apart from admin bans, so partial pages and uncertain Telegram failures cannot mislabel members.
- Stock notices use `stock_notification_events` plus service-only `stock_notification_recipients` on the authenticated notify tick: save rendered cards before fan-out, mark subscriptions only after customer delivery, use service-only claims with a shared lease and six-send pacing that releases untouched claims, honors retry_after and retries outages. Removal snapshots and counter-depletion triggers cover delete paths; after website-admin uploads attempt an immediate service-role queue drain without bypassing the durable event, with scheduled delivery as fallback. Paid broadcasts require approval.
- In-house stock counts come from `stock_counters`, kept exact by a trigger on `stock_items` (+1 add / -1 sold or deleted); `stock_counts()` reads it so bot clicks never scan thousands of items. Manual products with `manual_stock_limited` keep their admin-set count there and `take_manual_stock()` reduces it per paid order; unlimited stays the default.
- Admin stock extraction uses server-authorized, service-role-only atomic RPCs and per-admin export receipts containing IDs only; deletion locks and rechecks every exported row so sold stock cannot be removed, and original TXT content stays unmodified.
- Scheduled supplier sync skips parsing/matching/snapshot RPC when the supplier reply's SHA-256 fingerprint matches the last fully applied one, but forces a full run every 2 minutes and on manual/webhook runs.
- Reseller single-product GET uses bounded per-isolate caches (auth 30s keyed by API-key hash, product 10s keyed by reseller id + discount + product id) and throttled last_used_at writes; order/balance/transaction endpoints always authenticate live.
- Bot pre-orders are wallet-paid order rows with status `preorder`, drained oldest-first by `fulfillPreorders` (row lock via status flip to `preorder_processing`) after stock uploads and on every scheduled tick — serial delivery without a separate queue table.
- Keep Binance amount generation and matching in a pure shared helper with focused tests so direct checkout, wallet deposits, reseller top-ups and scheduled verification enforce the same payment rule.
- Send Telegram post-delivery appreciation through the shared credential-delivery helper only after Telegram accepts the complete delivery.
- OxaPay (crypto) is off by default (`oxapay_enabled`); website orders use `W-<orders.id>`, bot deposits `D-<binance_deposits.id>`, and every credit re-reads the invoice from OxaPay after HMAC check, so a forged webhook can never mark anything paid. Bot visibility and new attempts read current narrow gateway settings rather than the general bot cache; wallet and product checkout share the wallet registry icon; direct checkout keeps its snapshot on the deposit row and the verified settlement/fulfillment path.
- Checkout payment branding uses local imported image assets inside design-system selection buttons; artwork changes must not affect gateway availability or payment handlers.
- Safe projections: public product readers use the server-only `public_products` view (raw `products` stays admin-only through RLS); reseller product/order responses use explicit projections with fixed client-safe database errors; customer order history uses a service-role-only RPC after verified authentication so raw orders.meta never reaches customers, while admin RLS stays intact.
- Reseller webhook saving and sending share HTTPS/public-DNS checks and never follow redirects; DNS preflight does not pin resolution and is not complete DNS-rebinding protection.
- Public payment cron routes must fail closed and accept scheduler credentials only in headers, never URLs.
- Fulfill charged reseller own-stock orders through the service-role-only atomic stock/order RPC in normal purchase and recovery; run bounded recovery on the existing notify tick so interruptions cannot cause repeat debits or orphaned stock claims.
- Telegram catalogue rules live in shared pure helpers: favorites use the entire visibility/availability-filtered catalogue, grouped and paginated before user prices (legacy saved picks do not restrict it, distinct same-name rows survive); category visibility keeps empty active channel-permitted categories, loads sold-out rows only for valid category browsing, and filters availability explicitly for favorites/All Products.
- Admin supplier/reseller colour chips take their hues from `src/lib/supplier-colors.ts` so one supplier keeps one colour everywhere; new screens import them instead of redefining a palette.
- The Telegram price-list post uses shared pure batching/Markdown helpers; generation advances the preview cursor, authenticated sending validates and uses only the preview snapshot while resolving recipients server-side. Send via `sendRichMessage` with HTML fallback; emoji settings use `productListSettingKey` so preview, send and tests share one format.
- Gateway bot checkouts settle wallet credit, original-order debit and paid status through the service-role-only atomic settlement RPC; expiry locks the same deposit first. Paid pricing comes from reserved orders, and unavailable products retain payment in the wallet.
- EPS IPNs dispatch to bot or website settlement by stored transaction IDs and always reverify remotely; wallet credit excludes payer fees and uses the requested USD amount; existing sweeps recheck late attempts before expiry.
- Order timestamps retain stored UTC instants and use a shared explicit display timezone default instead of browser-local or Karachi fallback.
- In-house retry uses a service-role-only atomic stock/order RPC and reuses saved delivery; unpaid/refunded orders cannot claim stock and retry never debits a wallet. Mobile and desktop actions share `canRetryInhouseOrder` so completed or non-recoverable orders never expose it; supplier API actions stay separate.
- Live updates use error-swallowing DB triggers into live_update_events and the existing notify tick. Bot/website/reseller sales are masked purchase posts with no customer emails; livePostKeyboard links Buy Now to the configured bot, resolving icons server-side by order/product IDs in bounded reads; top-up/member posts stay plain.
- Reseller recovery uses rate-limited Supabase resetPasswordForEmail and public /reset-password with verified recovery sessions; updateUser sends only password, preserving profiles and never storing tokens. Recovery/login stay open during maintenance.
- Supplier sync never overwrites an existing supplier product's texts (name, description, important_note, quick_guide, image_url, delivery_time, details) — patches come from the pure `existingProductSyncPatch` in `src/lib/suppliers/sync-patch.ts` (stock, price, supplier-off `is_active: false` only); new products still receive supplier texts when first listed.
- Admin orders render through the shared `OrderCard` (one order per card on every screen size) with the dense table kept behind a persisted Cards/Table toggle; browser-storage view state is read only after hydration so server markup never mismatches.
- Admin theme choice is provided once around the root shell, allowlisted and browser-persisted after hydration; router-scoped document-root skin classes theme login, admin wrappers and body-mounted portals consistently, while non-admin routes remove the scope and both palettes stay centralized in global CSS.
- Telegram welcome tables use a pure builder and shared send/edit rich HTML dispatch with existing keyboards; only definitive format rejection falls back to regular HTML, preventing duplicate sends after uncertain failures.
